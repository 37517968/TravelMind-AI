# 正式环境受控容量探测（2026-09-27）

## 1. 测试约束

- 环境：`http://101.34.30.32/api`，正式环境但尚未大规模开放；
- 原则：小样本阶梯加压，真实新任务不超过 10 个，发现明显排队后停止；
- 本轮新增真实 Agent 任务：6 个（幂等提交 1 个、并发 1 阶段 2 个、并发 2 阶段 3 个）；
- 没有进入并发 4，因为并发 2 已出现明显用户体验退化且吞吐增益很小；
- 限制：测试机无法访问服务器内网 Prometheus，因此本报告是黑盒容量探测，没有 CPU、JVM、RabbitMQ backlog、MySQL 与模型供应商指标。

## 2. 结果汇总

| 层级 | 请求模型 | 成功率 | 吞吐 | P95 | 结论 |
|---|---|---:|---:|---:|---|
| 任务详情旧接口 | 20 次 / C2 | 95% | 0.669 req/s | 3743 ms | 接口同时加载任务大字段与全部 Checkpoint，不适合作为高频状态轮询 |
| 幂等任务提交 | 50 次 / C4 / 同一 Key | 100% | 69.694 req/s | 113.703 ms | 全部返回 taskId=47，只创建 1 个真实任务；这是重复提交能力，不是真实任务完成 QPS |
| RAG 搜索 | 20 次 / C2 | 100% | 16.325 req/s | 462.488 ms | 预热后稳定；早期 3 次冒烟出现过 4415 ms 长尾，仍需长时间观察 |
| Agent + SSE | 2 个 / C1 | 100% | 0.040 task/s（2.37/min） | 首事件 653 ms；首 Token 5169 ms；完成 26353 ms | 当前单任务体验可接受 |
| Agent + SSE | 3 个 / C2 | 100% | 0.043 task/s（2.59/min） | 首事件 23971 ms；首 Token 27753 ms；完成 44709 ms | 吞吐仅提升约 9%，首 Token/完成延迟显著恶化，已达到当前有效容量边界 |

小样本下 P95 基本等于较慢样本，不能视为长期统计分位数，但足以支持“不要继续提高并发”的本轮停止条件。

## 3. 当前容量判断

- **接入层幂等提交能力**：本轮约 `69.7 req/s`，但这是相同请求的去重热路径；不得写成 69.7 个 Agent/s。
- **RAG 黑盒吞吐**：本轮约 `16.3 query/s`，仅代表当前 6 类重复查询与缓存/索引状态。
- **Agent 完成吞吐**：当前约 `0.04 task/s`，即 `2.4～2.6 task/min`。
- **建议的初始在线准入速率**：在完成更长稳态测试前，保守限制为 `0.02 new task/s`（约 1.2 个新任务/分钟），允许不超过 2 个任务的短突发。该值是按本轮完成速率预留约 50% 排队余量的工程建议，不是新的实测点。
- **当前推荐并发**：单个 Agent Worker 保持 1 个立即执行任务；额外任务进入队列。并发 2 虽未失败，但首事件与首 Token 已明显排队，不适合直接作为用户侧默认并发。

## 4. 已确认的瓶颈

1. `GET /agent/tasks/{id}` 调用 `AgentTaskService#get`，每次读取完整 `agent_task`（含 request/result JSON）并执行 `checkpointMapper.selectByTaskId` 加载全部检查点。压测代码已增加 `/agent/tasks/{id}/status` 轻量投影，只读取状态、节点、用量和时间字段；部署后应使用相同参数做 A/B 复测。
2. 生产配置默认 `AGENT_WORKER_CONCURRENCY=1`、`prefetch=1`。虽然最大并发默认允许扩到 4，但短任务突发期间动态消费者未及时带来吞吐增长，表现为并发 2 时首事件等待约 20 秒。
3. 当前缺少本轮 Prometheus 数据，尚不能判断真正限制来自 Rabbit 消费并发、模型并发、地图工具、数据库还是 CPU。部署本次指标代码并从服务器本地执行下一轮后才能归因。

## 5. 下一轮验证

1. 部署轻量状态接口与 SSE 活跃连接指标；
2. 在服务器本地设置 `PROMETHEUS_URL=http://localhost:9091`，采集 queue delay、Rabbit ready/unacked、节点 P95、模型首 Token、Tool/RAG、JVM 和连接池；
3. A/B 测试 `AGENT_WORKER_CONCURRENCY=1` 与 `2`，每档只运行 6～10 个固定请求；
4. 若并发 2 能把首事件恢复到 2 秒以内且没有模型/高德限流，再测试双 Worker 副本；
5. 最后执行 30～60 分钟、约 1 task/min 的稳态测试，验证队列不会持续增长。
