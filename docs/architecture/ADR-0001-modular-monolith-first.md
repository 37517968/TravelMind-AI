# ADR-0001：先模块化单体，后按压力拆分

- 状态：Accepted
- 日期：2026-09-19

## 背景

当前项目是一个 Spring Boot 应用。Agent、RAG、社区、工具和用户模块尚未形成稳定的独立扩容边界，直接拆分大量微服务会增加远程调用、部署和数据一致性成本。

## 决策

Phase 0～2 保持单仓库、单应用，但按 `task`、`harness`、`memory`、`rag`、`tool`、`community`、`knowledge`、`infrastructure` 建立模块边界。先把会话、任务和索引状态外置，再根据实际压力拆分 Agent Worker、Knowledge Worker 和 Community Service。

## 理由

- 当前团队和业务规模不需要大量独立服务；
- 模块化单体仍可通过包边界、接口和事件实现低耦合；
- 状态外置后，拆分部署单元的迁移成本更低；
- 可以先得到可靠的性能基线，再决定拆分位置。

## 后果

- 近期不能把“微服务架构”写成已实现能力；
- 需要禁止跨模块随意访问 Mapper；
- 后续服务拆分必须由独立扩容、故障隔离或团队边界驱动。

## 复审条件

当 Agent Worker、知识索引或社区流量出现明显不同的扩容需求时复审。
